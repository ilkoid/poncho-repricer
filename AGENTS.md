# AGENTS.md — конвенции poncho-repricer

Репрайсер для маркетплейсов Wildberries и Ozon: управление ценообразованием
(в перспективе — и продвижением). Проект ведётся по правилам соседних
`poncho-ai` / `poncho-oz`. При конфликте документов приоритет: этот файл,
затем AGENTS.md и практика `poncho-ai`.

> **Статус: Фаза 0 — сбор бизнес-требований.** Ожидания собираются от генерального
> директора и директора по ассортименту и товародвижению; затем отрабатывается
> методика. Архитектурные решения (хранилище, форма сервиса) принимаются
> **после** Фазы 0 под требования — скелет до тех пор их не фиксирует.

## 1. Роли и дисциплина изменений

- Пользователь — архитектор и постановщик бизнес-требований; архитектурные
  решения за ним.
- AI-агент — разработка и сопровождение. Существенные решения (новые внешние
  зависимости, схема БД, форма сервиса, изменение контрактов) — предлагать
  с обоснованием, не вводить молча.
- Принципы изменений как в `poncho-oz/ai_manifest.md`: Understand Before
  Modifying, Smallest Correct Change, Extend Before Creating.

## 2. Стек

- Бэкенд — Go 1.26; HTTP — stdlib `net/http`, если пользователем не согласовано иное.
- Фронтенд — TypeScript, **vanilla, без фреймворков** (`web/`); из инструментария
  только vite (сборка + дев-сервер) — по аналогии с `extensions/poncho-wb-parser`
  в poncho-ai.
- Новые библиотеки (и Go, и TS) — только с явным обоснованием в задаче:
  что даёт, почему stdlib/существующего кода недостаточно.

## 3. Переиспользование — главный принцип

Код не дублируется. Прежде чем писать новое — найти готовое у соседей:

- `../poncho-ai` (модуль `github.com/ilkoid/poncho-ai`):
  - `pkg/wb` — клиент WB API: адаптивный rate-limit, retry, цены (`GetPrices`),
    продвижение/ставки (advert API), стоки, продажи;
  - `pkg/prices` — домен загрузки цен (Source/Writer); `pkg/storage/postgres` —
    пул pgx и репозитории; `pkg/storage/sqlite` — legacy, здесь не использовать;
  - `pkg/config` — YAML-загрузчик с подстановкой `${VAR}`;
  - `pkg/dllog` — логирование загрузчиков; `pkg/cardupdate` — применение
    card-мутаций (эталон паттерна «рекомендация → применение»).
- `../poncho-oz` (модуль `github.com/ilkoid/poncho-oz`): `pkg/oz` — клиент Ozon
  Seller API. Пока покрывает только словарные эндпоинты каталога — расширяется
  **в нём самом** (новые эндпоинты цен/продвижения добавляются в poncho-oz,
  а не клонируются сюда).
- Механизм импорта: в `go.mod` — GitHub-пины (переносимость), локально живой код
  соседей подставляется через `go.work` (в `.gitignore`, не коммитится).
  Gotcha: без `go.work` (другая машина / чистый клон) сборка идёт по GitHub-пинам —
  тогда свежие изменения poncho-ai/poncho-oz должны быть запушены, а пин обновлён
  (`go get <module>@master && go mod tidy`).
- Сюда НЕ копируются: swagger-спеки (канон — `../poncho-ai/docs/`, см. §5)
  и куски клиентов «на всякий случай».

## 4. Структура репозитория

- `cmd/<name>/` — точки входа: только init + оркестрация, вся логика в `pkg`/`internal`.
  Рядом лежит `config.yaml` команды.
- `pkg/` — переиспользуемая библиотека; не импортирует `internal/`.
  Домены `pkg/<domain>/` — интерфейсы Source/Writer + логика, без деталей HTTP/pgx.
- `internal/` — прикладная логика, недоступная внешним модулям.
- `pkg/storage/postgres/` — репозитории `Pg*Repo` (pgx), `InitSchema` + batch upsert.
- `web/` — фронтенд (vanilla TS).
- Для ручного запуска команд — простой `.sh` в корне: грузит `.env`, зовёт
  `go run .`, **пишет лог** (см. §8).

## 5. Спецификации API (swagger) — где искать

- WB: `../poncho-ai/docs/wb_api_swagger/` — 13 нумерованных YAML
  (продвижение/advert — `06-promotion.yaml`; цены — discounts-prices; и т.д.).
- Ozon: `../poncho-ai/docs/ozon_api_swagger/ozon_api.json` (зеркало — poncho-oz).
- Искать пути/схемы/rate-limits — только там; сюда спеки не копировать;
  обновляются они в poncho-ai (задача `download-api-specs`).

## 6. Конфигурация и секреты

- YAML-first: `config.yaml` рядом с командой; `${VAR}` подставляются из окружения.
- Секреты — только в локальном `.env` (формат `export VAR='...'`, в `.gitignore`);
  шаблон — `.env.example`. Имена переменных совместимы с poncho-ai
  (`WB_API_KEY`, `WB_API_CONTENT_KEY`, `OZ_CLIENT_ID`, `OZ_ADMIN_API_KEY`, …).
- Хардкод секретов, эндпоинтов и rate-limit'ов в коде запрещён.
- В логах ключи и чувствительные данные не светить.

## 7. База данных

- Решение о хранилище (PostgreSQL vs SQLite) **открыто** — принимается после
  Фазы 0 под требования и методику. У обоих вариантов есть проверенный слой
  в poncho-ai: `pkg/storage/postgres` (pgx/v5) и `pkg/storage/sqlite`.
- Тестовые БД — `*_test`, продовые — `*_prod`. Таблицы — с префиксом домена.
- Схема — через `InitSchema` в `*_schema.go` (DDL отдельными `Exec`), как у соседей.

## 8. ⛔ Безопасность записи — абсолютные правила

- Агент пишет **только в тестовые БД** (`*_test`). Любой INSERT/UPDATE/DELETE/DDL
  в `*_prod` запрещён: агент готовит проверенные SQL/команды, пользователь
  выполняет их сам (copy-paste или скрипт).
- Записи в API маркетплейсов (цены, ставки, кампании, карточки) агент на реальном
  кабинете **не выполняет**. Формат работы: `--dry-run` / тестовый кабинет /
  sh-скрипт для запуска пользователем вручную.
- Тестовый контур: у **WB есть песочница** с отдельным API-ключом — записи WB
  отрабатываются там. У **Ozon песочницы нет вообще** — записи Ozon только
  dry-run + ручной запуск; стратегия тестирования Ozon прорабатывается отдельно
  (кандидат: мок-клиент по swagger — паттерн `mock_client` из poncho-ai).
- Скрипты и утилиты для действий на проде **обязаны писать логи**: файл с
  таймстемпами, параметрами запуска и результатом шагов — чтобы агент мог
  разобрать инцидент по логам после запуска.
- Read-only (GET/POST-чтение API, `SELECT` в БД) допустим; на прод-данных —
  без побочных эффектов и без выгрузки лишнего объёма.
- Сомневаешься, запись это или нет — считать, что запись, и спросить пользователя.

## 9. Тестирование — минимальные сценарии

- Датасеты и сценарии минимальны: 2–3 артикула/кампании, не весь каталог.
  Цель — проверить логику, а не объём; время тестирования не затягивать.
- Прогонять «все артикулы / все программы продвижения» через API в тестах
  **запрещено** — только выборка по swagger (§5).
- Живые API в автоматических тестах — только read-only и выборочно
  (конкретный nmID/кампания).
- Юнит-тесты — быстрые, без сети; `go test ./...` проходит локально.
- Имена WB-сущностей (nmID и др.) — BIGINT.

## 10. Качество кода и команды

- Идиоматичный Go: `fmt.Errorf("...: %w", err)`, `errors.Is`/`errors.As`,
  `context.Context` пробрасывается везде, без `panic()` в бизнес-логике,
  потокобезопасность по умолчанию (`sync.RWMutex`), буферизованные каналы.
- Дублирование кода недопустимо: сначала поиск по poncho-ai / poncho-oz /
  этому репо, потом новая реализация.
- Перед коммитом — полный набор проверок:

```bash
go build ./... && go vet ./... && go test ./...   # бэкенд: сборка/статанализ/тесты
(cd cmd/repricer && go run .)                     # запуск скелета с config.yaml
(cd web && npm run build)                         # фронт: tsc --noEmit + сборка vite
(cd web && npm run dev)                           # фронт: дев-сервер
./create-test-db.sh                               # тестовая БД (когда решим хранилище)
```
